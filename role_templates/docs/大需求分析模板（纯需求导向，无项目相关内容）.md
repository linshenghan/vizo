# 单一需求分析模板（纯需求导向，无项目相关内容）

# 1. 需求概述

明确待分析的**核心需求**（简洁表述，1句话说清：用户想要通过什么方式，解决什么问题/达成什么目标）：

[填写核心需求，例：用户希望有一款便捷的手机端文档编辑工具，可离线编辑并自动同步]

# 2. 用户分析（核心）

明确该需求对应的目标用户，聚焦“谁会有这个需求”，不冗余：

- 核心用户：[填写核心用户群体，例：经常外出办公的职场人、学生]

- 用户特征：[简要补充用户关键特征，例：移动办公频繁、无稳定网络、需快速编辑文档]

- 用户核心诉求：[关联需求本身，例：无需依赖网络即可编辑，编辑后自动同步，避免数据丢失]

# 3. 用户痛点分析

## 3.1 核心痛点

明确用户因该需求未被满足，产生的具体困扰（聚焦核心，不罗列次要痛点）：

- [痛点1，例：外出时无网络，无法编辑文档，紧急需求无法响应]

- [痛点2，例：离线编辑后需手动同步，易遗漏、易丢失数据，操作繁琐]

## 3.2 痛点产生原因

分析痛点出现的核心原因（不涉及解决方案，仅说明“为什么会有这个痛点”）：

- [原因1，例：现有文档工具多依赖网络，无离线编辑功能或离线功能不完善]

- [原因2，例：离线与在线数据同步机制缺失，需用户手动操作，易出错]

# 4. 痛点场景还原（用户故事）

以真实用户视角，还原痛点出现的具体场景（1-2个核心场景，贴合用户特征，有代入感）：

- 场景1（用户故事）：[例：职场人小李出差途中，接到领导紧急通知，需修改一份方案文档，但高铁上无网络，现有文档工具无法离线编辑，导致无法及时响应，耽误工作进度]

- 场景2（用户故事）：[例：学生小张在图书馆（无网络区域）编辑论文，离线编辑完成后忘记手动同步，回家后发现数据未保存，辛苦编辑的内容丢失，需重新撰写]

# 5. 痛点可解决性分析

明确该用户痛点是否可被解决，说明核心依据（客观判断，不夸大）：

- 可解决性：[是/否/部分可解决]

- 核心依据：[例：是，现有技术可实现手机端离线存储、离线编辑，以及网络恢复后的自动同步功能，无技术壁垒；且用户痛点明确，无不可逾越的客观限制]

# 6. 痛点解决思路（核心）

针对核心痛点，给出明确的解决思路（聚焦“如何解决”，不涉及具体操作、界面设计，简洁明了）：

- 针对痛点1：[解决思路，例：开发离线编辑功能，支持文档本地存储，无网络时可正常编辑、保存]

- 针对痛点2：[解决思路，例：添加自动同步机制，网络恢复后，离线编辑的内容自动同步至云端/其他设备，无需用户手动操作]

# 7. 解决价值分析（专业版）

核心：围绕「用户痛点解决」「商业/市场竞争力」展开，优先量化价值（可落地、可验证），明确价值优先级，关联前文痛点及竞品不足，避免空泛描述，同时补充潜在价值，体现前瞻性。

- **用户价值（核心优先级）**：[量化+定性结合，关联前文痛点，例：1. 效率价值：解决无网络编辑痛点，将外出场景下文档编辑响应效率提升60%以上，紧急需求响应延迟从几小时缩短至1分钟内；2. 体验价值：解决数据同步繁琐、丢失痛点，将离线编辑数据丢失率降至0.1%以下，减少80%手动同步操作，降低用户时间成本；3. 场景价值：覆盖高铁、图书馆等无网络场景，满足移动办公/学习人群的核心使用诉求，提升用户粘性]

- **市场价值（次要优先级）**：[关联竞品分析，体现差异化，例：1. 差异化价值：针对竞品“离线与同步不可兼得”的不足，打造“离线编辑+自动同步”一体化能力，填补细分场景空白；2. 竞争力价值：覆盖目标用户群体（移动办公族、学生）约5000万+潜在用户，可提升产品市场占有率3%-5%；3. 商业潜在价值（可选）：若为商业化产品，可基于该功能设计增值服务（如大容量离线存储），拓宽变现路径]

- **潜在价值（补充）**：[例：1. 产品迭代价值：沉淀离线存储、自动同步技术能力，可复用至后续其他场景（如离线表单、离线笔记）；2. 用户口碑价值：解决行业核心痛点，易形成用户自发传播，提升产品品牌影响力]

- **价值优先级说明**：用户价值＞市场价值＞潜在价值，优先保障核心用户价值落地，再同步挖掘市场及潜在价值，避免“为了做功能而做功能”，确保价值与痛点强绑定

明确痛点解决后，对用户、市场的核心价值（量化优先，无量化则明确定性价值）：

- 用户价值：[例：提升用户办公/学习效率，避免数据丢失，减少手动操作成本，解决无网络场景下的编辑需求，提升用户体验]

- 市场价值（可选）：[例：覆盖移动办公、离线场景的用户群体，填补现有工具的功能空白，增强产品竞争力]

聚焦同类需求/痛点，分析市场上现有竞品的解决方式、优势与不足（简洁对比，不冗余）：

|竞品名称|痛点解决方式|优势|不足|

# 9. 需求合理性评估

客观评估该需求的合理性，明确合理/不合理/部分合理的判断及核心依据，贴合用户痛点、解决价值及实际可行性：

- 合理性判断：[合理/不合理/部分合理]

- 核心依据：[例1：合理——用户痛点明确、有实际解决价值，技术可实现且无重大约束，贴合目标用户核心诉求；例2：不合理——痛点非核心需求，解决成本过高，与用户实际使用场景脱节，无明显市场/用户价值；例3：部分合理——核心诉求有价值，但需求范围过宽/过细，存在可优化空间]

# 10. 需求改进建议（如有）

针对需求的不合理之处、可优化点，给出具体、可落地的改进建议，贴合前面的痛点、解决思路及合理性评估：

- [建议1，例：若需求范围过宽，建议聚焦核心痛点，删减非必要诉求，优先落地核心功能，后期逐步迭代]

- [建议2，例：若解决成本过高，建议优化解决思路，采用更简洁、低成本的方案，兼顾需求满足度与可行性]

- [建议3，例：若需求贴合用户痛点但细节不足，建议补充具体场景诉求，明确需求边界，避免后续歧义]
